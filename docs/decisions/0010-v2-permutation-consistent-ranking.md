# ADR 0010 — Investigate alias and row effects, then test permutation-consistent ranking

Date: 2026-10-19. Status: accepted research direction; implementation and new measurements pending. This decision adopts the useful direction of the supplied external review without changing the historical v2 results, checkpoints, or release claims. Keep the name **v2 research**; a v3 rename requires a separate release decision.

## Evidence and problem

The frozen [S0b candidate-order diagnostic](../research/v2_candidate_order_protocol.md) changed the top candidate on 65/180 Swissmetro episodes, 10/20 ESCI groups, and 12/15 eligible Expedia searches. These are small, already-consulted validation cohorts. Every S0b scored pair had zero prompt overflow. The existing two-order test shuffles rows and reassigns aliases together: [`_render_projection`](../../src/liquid_mcdm/training/behavioral_rendering.py) builds `opt{i}` from row position; upstream Choice rendering/readout then maps those slots to token aliases. It proves sensitivity to that *joint* intervention, but cannot attribute flips to row position, aliases, or their interaction. Repeated inference and token-group behavior are also unmeasured in this diagnosis.

The bounded [neural held-out probe](../research/v2_neural_heldout_protocol.md) is exploratory and has been consulted: Swissmetro base/S0b top-1 was 306/450 versus 298/450, ESCI NDCG@10 was 0.705590 versus 0.714332 on 50 groups, and Expedia conditional-booking top-1 was 2/29 versus 4/29. S0b changed several training conditions at once; none of these deltas isolates permutation augmentation. The [Expedia LambdaRank 0.413110](../plans/2026-10-18-v2-training-execution.md) is 0/1/5 click/booking relevance NDCG@10 over a separate 5,000-search pool. It cannot be compared with conditional-booking choice accuracy or called a matched neural baseline.

## Decision and alternatives

1. **Pause further RL continuation** while representation and ranking stability are unresolved. Retain base d1, S0 and S0b as immutable controls, including their receipts. The completed RL-style continuation was a bounded stochastic pilot, not evidence that every GRPO/RLCD design fails; planned GRPO branches were not run. Resume only after a fixed reward, stable scoring boundary, and independent evaluation.
2. **First run a validation-only frozen 2×2 diagnostic.** Use the exact same selected validation groups, checkpoint, feature policy, token limit, and eligible candidate set per source. Factor C changes the ordering of content rows while keeping each candidate ID's slot/alias fixed. Factor A rotates the ID-to-slot/alias assignment while leaving content-row order fixed. C0A0 is the current prompt. C1A0 changes rows only; C0A1 changes aliases only; C1A1 applies both independent interventions. Keep the option list and readout slot order fixed in all four cells. This differs from the historical joint shuffle, which assigned slots afresh by the shuffled row order. Retain that historical joint operation as a fifth, explicitly labeled control if exact reproduction is needed. The diagnostic may require a validation-only rendering seam; default production/pilot rendering must remain byte-identical. A cell that cannot be represented without changing the question or feature policy is a failed design, not a silent substitution.
3. **Then compare two numerical shared-scorer arms** on matched target, pool, groups and features: independent per-candidate scores `s_i = h(z_i)` and a masked Deep Sets context arm `s_i = h(z_i, mean_{j:mask_j} phi(z_j), log1p(count))`. `z_i` comes from one shared candidate/context/numeric encoder. Both are equivariant to candidate permutation by construction when implementation honors masks and excludes order features. The independent arm tests whether set context is useful; the set arm allows alternatives to influence one another. Optional Set Transformer attention is a *separate* interaction arm only if a documented error slice justifies its extra cost. [Deep Sets](https://papers.nips.cc/paper/6931-deep-sets) and [Set Transformer](https://proceedings.mlr.press/v97/lee19d.html) motivate these architectures; they do not establish performance on Ordivo data.
4. **Add a per-candidate text body only after numerical evidence.** Evaluate the official [LFM2.5-Encoder-350M](https://huggingface.co/LiquidAI/LFM2.5-Encoder-350M) as a frozen, shared text encoder first, then consider unfreezing after measured gains. Its card describes a ~354.5M-parameter masked language model with 1024 hidden size and 8192-token context; use a pinned revision and audit `trust_remote_code` before any remote import. Encode context and each candidate independently with shared weights. Concatenating a whole candidate list through a sequential backbone does not inherit equivariance from a set head.

No result is accepted merely because a numerical permutation test passes. Invariance is score equivariance after mapping by candidate ID, within a **predeclared tolerance per dtype/device at evaluation**; bitwise equality is not required. Near ties require a separately declared canonical-ID tie policy. Set awareness does not imply independence of irrelevant alternatives; changing the set may legitimately change relative scores. Candidate order alone must not.

## Data and decision boundaries

- Use a fixed, named, versioned feature schema per domain and objective. Fit numeric transforms only on training data, retain missing flags and units, and ban IDs, row/position/exposure, target, and provenance fields from predictor features. Existing [`inference_input`](../../src/liquid_mcdm/data/behavioral.py) is the source projection boundary. Criteria that differ between requests require explicit schema/criterion-encoder support and their own evaluation; the first fixed-schema benchmark does not prove arbitrary-criteria reasoning.
- Preserve complete candidate groups and masks. Exclude padded and unavailable candidates from set summaries, scoring eligibility, losses and metrics. An all-infeasible request is a decision-layer `no_feasible_alternative` result, never an empty neural softmax. Any prompt/token limit is reported as coverage failure; no top-K substitution, truncation, or silently dropped alternatives.
- Keep preference resolution and exact claim verification separate from learned scores. Reuse [`decision/weights.py`](../../src/liquid_mcdm/decision/weights.py) and [`decision/verification.py`](../../src/liquid_mcdm/decision/verification.py). Benchmark user-supplied, approved-policy, externally supplied learned-evidence, objective and unknown-weight modes; no learned preference profile generator exists yet. Unknown or conflicting preferences require an explicit unknown/scenario or abstention outcome, not fabricated authoritative weights. Verify a claim under its stated weights with the exact solver; neural scores alone do not certify an MCDM formula.
- Preserve four group-disjoint roles from [ADR 0009](0009-v2-four-role-splits.md): train, selection validation, calibration, final test. The existing exploratory test subsets, and possibly source test artifacts used by classical benchmarks, require an exposure audit. Merely removing the neural 50-unit slice cannot certify the remainder as untouched. A future final claim requires a newly protected/source-heldout cohort, frozen manifests, and source-specific rights checks.
- Compare matched objectives separately: Swissmetro stated choice clustered by respondent, ESCI official-gain relevance clustered by query, Expedia exposed-search combined relevance clustered by search; conditional booking is a separately selected exactly-one-booking task. Report paired group/bootstrap intervals and seed variation separately. Predeclare 42/43/44 as candidate training seeds before execution; these are **proposed, not run**. Never pool unlike metrics into a cross-domain macro claim.
- Report natural complete-group size bins at 5, 10, 20, 50 and 100+ where available. Synthetic stress sets are separately labeled and must retain valid labels and complete groups; deleting options can change the task and winner. Include missingness, text length, latency, memory and coverage. A numerical CPU correctness check precedes a remote GPU device/VRAM probe and bounded experiment. Record spend ceiling, timeout and operator cleanup controls before paid allocation.

The [implementation plan](../superpowers/plans/2026-10-19-v2-permutation-consistent-ranking.md) defines the next gates. No new model, diagnostic result, GPU run, preference learner, or release certification is delivered by this ADR.
